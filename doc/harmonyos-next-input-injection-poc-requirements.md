# HarmonyOS NEXT 输入注入权限验证 PoC 需求文档

## 1. 文档目的

本文档用于指导另一台开发机器上的工程师，独立完成 HarmonyOS NEXT 平板端输入注入能力验证 PoC。

PoC 的目标不是实现完整的 Input Leap 客户端，而是尽快回答一个关键问题：

**第三方应用在 HarmonyOS NEXT 平板上，是否可以实现满足 Input Leap 客户端要求的全局输入注入能力。**

这里的"全局输入注入"是指：

- 注入键盘按键事件（KeyDown / KeyUp）
- 注入鼠标或触控点击事件
- 注入鼠标移动、相对移动或等价的指针移动能力
- 在目标应用不受控、非本应用前台页面时仍然有效

如果该问题不能成立，则 HarmonyOS NEXT 客户端方案需要降级为无障碍替代方案，或者终止该平台适配。

## 2. PoC 范围

本次 PoC 同时验证两条路径：

- **路径 A：系统级输入注入 API 验证**
- **路径 B：无障碍服务替代方案验证**

本次 PoC 明确不做以下内容：

- 不实现完整的 Input Leap 协议对接
- 不实现 GUI 配置界面
- 不实现 HarmonyOS 服务端
- 不实现完整剪贴板同步
- 不追求产品化交互
- 不做长期保活优化

## 3. 背景与约束

### 3.1 业务背景

目标产品形态如下：

- 桌面端继续使用现有 Input Leap 服务端
- HarmonyOS NEXT 平板仅作为客户端被控端
- 不需要 HarmonyOS GUI，最小可接受形态是命令行逻辑 + 最小宿主壳
- 不需要在 HarmonyOS 上实现服务端能力

### 3.2 技术背景

现有 Input Leap 架构中，网络协议和客户端主流程是可复用的，真正决定平台能否支持的关键在于平台输入后端。

Android 参考项目 `mo3rfan/synergy-android-cyanogen` 的结论已经明确：

- 其核心机制是 `root + /dev/uinput + JNI`
- 它不是普通应用权限方案
- HarmonyOS NEXT 不能直接照搬 Android 的 `uinput` 思路

因此，HarmonyOS NEXT 必须验证其自己的输入能力边界。

### 3.3 约束条件

- 必须基于真机验证，模拟器结果不能作为最终结论
- 必须在未修改系统源码的前提下验证第三方应用能力
- 如需系统签名、厂商白名单、预装权限，必须在结论中明确标注
- 每个验证结论都要附带复现步骤、日志证据和屏幕录制证据

## 4. PoC 成功标准

### 4.1 路径 A 成功标准

满足以下全部条件，判定路径 A 成功：

1. 应用可在 HarmonyOS NEXT 真机上启动
2. 应用可调用系统级输入注入接口或等价能力
3. 可成功注入以下事件中的至少 3 类：
   - 单击
   - 双击
   - 键盘字符按下/抬起
   - 功能键或方向键
   - 相对移动或可替代的指针移动
4. 注入行为对第三方应用生效，而非仅限本应用内部
5. 输入行为不依赖手动点击当前页面中的特定控件树
6. 结果可重复，成功率不低于 90%

### 4.2 路径 B 成功标准

满足以下条件，判定路径 B 可作为降级备选方案：

1. 无障碍服务可正常启用
2. 可稳定完成以下动作中的至少 2 类：
   - 查找节点并点击
   - 查找输入框并写入文本
   - 滚动列表
   - 激活已知控件
3. 对至少 2 个第三方应用验证成功
4. 能明确列出其限制边界，例如：
   - 只能操作存在无障碍节点的界面
   - 无法模拟任意按键
   - 无法精确复现鼠标连续移动

### 4.3 总体成功判定

- **结论 A：主路径成立**
  - 系统级注入可行，且不需要不可获得的特权
- **结论 B：仅降级路径成立**
  - 系统级注入不可行，但无障碍方案可覆盖部分需求
- **结论 C：两条路径都不成立**
  - HarmonyOS NEXT 不适合作为该项目的客户端目标平台

## 6. 实施方案

## 6.1 路径 A：系统级输入注入验证

### 6.1.1 验证目标

验证第三方应用是否能够通过 HarmonyOS NEXT 的系统输入能力，对第三方应用进行全局输入注入。

### 6.1.2 预期技术路线

建议优先查找并验证以下方向：

- OpenHarmony / HarmonyOS NEXT 输入子系统相关 API
- `multimodalinput_input` 相关公开接口
- `inputEventClient`、`InputManager` 或等价接口
- C++ Native API 或 ArkTS 可调用接口
- 是否需要系统签名权限

### 6.1.3 最小实现要求

PoC 页面上至少提供以下按钮：

- `检查注入能力`
- `发送按键 A`
- `发送方向键 Left`
- `发送单击`
- `发送双击`
- `发送移动事件`
- `导出日志`

### 6.1.4 测试对象

至少选择以下目标之一进行验证：

- 系统设置页面
- 备忘录类应用
- 浏览器
- 任意第三方文本输入应用

### 6.1.5 关键验证点

每个动作都要回答以下问题：

1. 调用接口是否成功
2. 是否报权限错误
3. 是否只在本应用内生效
4. 是否对其他应用生效
5. 是否需要前台焦点
6. 是否需要手工授权特殊权限
7. 是否需要系统签名
8. 是否需要预装或厂商环境

### 6.1.6 建议的代码结构

```text
entry/
  src/main/
    ets/
      pages/
        Index.ets
      entryability/
        EntryAbility.ets
    cpp/
      CMakeLists.txt
      napi_init.cpp
      inject_test.cpp
      inject_test.h
```

### 6.1.7 建议的接口封装

Native 层建议暴露以下接口给 ArkTS：

- `checkInjectionCapability(): string`
- `injectKey(keyCode: number, action: number): number`
- `injectClick(x: number, y: number): number`
- `injectDoubleClick(x: number, y: number): number`
- `injectMove(x: number, y: number): number`
- `dumpLog(): string`

其中返回值建议统一为：

- `0`：调用成功
- 非 `0`：调用失败

同时输出详细日志。

### 6.1.8 路径 A 输出要求

必须输出一张结果表：

| 能力项 | 接口可调用 | 实际生效 | 是否跨应用 | 是否需系统权限 | 备注 |
|---|---|---|---|---|---|
| 键盘字符键 | 是/否 | 是/否 | 是/否 | 是/否 | 说明 |
| 方向键 | 是/否 | 是/否 | 是/否 | 是/否 | 说明 |
| 单击 | 是/否 | 是/否 | 是/否 | 是/否 | 说明 |
| 双击 | 是/否 | 是/否 | 是/否 | 是/否 | 说明 |
| 移动 | 是/否 | 是/否 | 是/否 | 是/否 | 说明 |

## 6.2 路径 B：无障碍服务替代方案验证

### 6.2.1 验证目标

验证在无法获得系统级输入注入能力时，HarmonyOS NEXT 无障碍服务是否能承担一个可接受的降级方案。

### 6.2.2 预期技术路线

建议优先查找并验证以下方向：

- `AccessibilityExtensionAbility`
- 无障碍节点检索
- `performAction()` 类动作接口
- 文本写入相关接口
- 滚动相关接口

### 6.2.3 最小实现要求

无障碍路径至少提供以下测试项：

- 启用服务后的状态显示
- 枚举当前界面节点
- 通过文本查找按钮并点击
- 查找输入框并写入文本
- 执行滚动动作
- 导出日志

### 6.2.4 测试对象

至少选择 2 个不同类型应用：

- 一个文本输入类应用
- 一个列表滚动类应用

### 6.2.5 关键验证点

1. 能否获取节点树
2. 能否稳定定位目标控件
3. 能否执行点击
4. 能否执行文本写入
5. 能否执行滚动
6. 对不同应用兼容性如何
7. 平均操作延迟是否可接受
8. 是否存在明显的误操作风险

### 6.2.6 路径 B 输出要求

必须输出一张结果表：

| 能力项 | 可实现 | 对第三方应用生效 | 稳定性 | 限制说明 |
|---|---|---|---|---|
| 节点点击 | 是/否 | 是/否 | 高/中/低 | 说明 |
| 文本写入 | 是/否 | 是/否 | 高/中/低 | 说明 |
| 列表滚动 | 是/否 | 是/否 | 高/中/低 | 说明 |
| 按键模拟 | 是/否 | 是/否 | 高/中/低 | 说明 |
| 连续移动 | 是/否 | 是/否 | 高/中/低 | 说明 |

## 7. 推荐开发步骤

建议严格按以下顺序执行：

### 第 1 步：环境准备

- 安装 HarmonyOS NEXT 开发环境
- 连接真机平板
- 确认可部署最小示例应用
- 验证日志抓取和录屏工具可用

### 第 2 步：建立最小工程

- 创建一个最小 Stage 应用
- 页面上显示若干测试按钮
- 接入日志输出能力

### 第 3 步：先做路径 A

- 先验证 API 是否存在
- 再验证调用权限
- 再验证动作是否实际生效
- 再验证是否跨应用生效

### 第 4 步：如果路径 A 失败，做路径 B

- 开启无障碍服务
- 验证节点遍历
- 验证点击
- 验证输入
- 验证滚动

### 第 5 步：整理证据与结论

- 汇总日志
- 保存录屏
- 输出结果矩阵
- 给出最终结论

## 9. 关键判定问题

最终报告必须明确回答以下问题，不能含糊：

1. 第三方应用能否做全局输入注入
2. 如果能，是否需要系统签名
3. 如果能，是否只在特定设备或厂商环境成立
4. 如果不能，无障碍方案是否足以支撑基础可用性
5. 无障碍方案能覆盖哪些场景，不能覆盖哪些场景
6. 是否值得继续做 HarmonyOS NEXT 客户端

## 11. 开发注意事项

- 不要在 PoC 阶段引入 Input Leap 完整协议栈
- 不要一开始就做长连接和后台保活
- 不要把无障碍方案误判为全局输入注入方案
- 不要只在本应用页面里验证就宣称成功
- 不要只看接口存在就判定可用，必须看跨应用实际效果
- 不要省略日志、录屏和失败证据

## 附：建议的执行优先级

优先顺序必须是：

1. 先确认接口是否存在
2. 再确认权限是否可申请
3. 再确认调用是否成功
4. 再确认跨应用是否生效
5. 再评估是否满足 Input Leap 需求

如果在第 2 步就确认必须依赖不可获得的系统签名，应立即在结论中标明主路径高风险，不要继续乐观推进。
